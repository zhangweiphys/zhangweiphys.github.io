noesis-knowledge 本地部署指南（其他模块可参考）

本文档记录从零开始部署 noesis-knowledge 并通过 python dev_cli.py 进入 CLI 的完整流程。
所有命令在 PowerShell 下执行（也适用 WSL/bash，命令同）。

0. 总览

安装策略（两种等价方法，二选一，详见第 7 步）：

  • noesis-contracts 用 pip install -e . 可编辑安装（它的 README「开发」节原文推荐），顺带装上它声明的依赖（pydantic / pydantic-settings / sqlalchemy / httpx / numpy / h5py / openai / scikit-learn / tiktoken / toml）。
  • noesis-knowledge 有两种等价装法：
    • 方法 A（--no-deps）：不动任何 tracked 文件，两条命令。
    • 方法 B（裸名变体）：临时把 pyproject.toml 里 contracts 依赖改成裸名，一条命令装完，再还原。
    • 两种方法装进 venv 的包集合与版本完全相同；B 元数据更干净（pip check 更稳）、且只一条命令。
  • 配置：复制 .env.example 为 .env 填 key（不再是 llm_config.local.toml）。

⚠️ 为什么不能直接裸 pip install -e . 装 knowledge：它的 pyproject.toml 第 10 行声明了
noesis-contracts @ git+https://gitee.com/PlasmaScience/noesis-contracts.git（PEP 508 直接 URL 依赖）。
裸 pip install -e . 会判定你本地的 file:/// 可编辑 contracts 不满足这条 git+https 依赖，于是去 gitee 重拉一份覆盖掉本地可编辑安装（详见附录 A）。方法 A 用 --no-deps 跳过；方法 B 把依赖改成裸名 "noesis-contracts" 让 pip 认定”已安装即满足”。

7. 安装 noesis-knowledge 本体 + 第三方依赖

noesis-knowledge/pyproject.toml 声明的第三方依赖（除 contracts 外共 13 个，均为 >= 下界）：

httpx>=0.24.0、mcp>=1.0.0、numpy>=1.24.0、pymupdf>=1.23.0、pypdf>=4.0.0、requests>=2.28.0、
scikit-learn>=1.3.0、tavily-python>=0.3.0。
其中 httpx、numpy、scikit-learn 已由第 4 步装好，pip 会自动跳过。

两种方法二选一。

方法 A：--no-deps（不改任何 tracked 文件）

输出 Successfully installed noesis-knowledge-0.1.0 即本体安装成功。

方法 B：裸名变体（一条命令，临时改 pyproject 再还原）

前提：contracts 已在第 4 步可编辑装好（已满足）。

裸名为何不重拉 gitee：附录 A 的问题根因是依赖写成 name @ git+https://... 直接 URL，pip resolver 认定”必须从该 URL 取”。改成裸名 "noesis-contracts"（无 URL、无版本）后，pip 发现 contracts 已装（0.1.0，无版本约束即满足）-> 判定已满足，不下载。

关于安装包版本（重要）

无论方法 A 的手动清单还是方法 B 的 pip install -e .，pip 都是按 >= 下界解析到各自最新版（兼容 Python 3.12 的最新），装的版本完全相同。因为 pyproject 全部依赖都是 >= 下界、无上界封顶，最新版必然满足全部 >= 要求，pip check 会通过。

  • pip install <names>（不带版本号、不带 .）**不会读 pyproject.toml**，它按包名从 PyPI 取最新版；但因为 pyproject 全是 >= 无上界，最新版天然满足，故 pip check 通过。
  • 隐患：无上界 -> “太新”可能踩 breaking change（典型 numpy 2.x 相对 1.x 的破坏性变更）。但此风险与装法无关，且 venv 里 numpy 等在第 4 步装 contracts 时就已经是 latest。

9. 配置 LLM API Key（新三件套：config.toml + providers.toml + .env）

dev_cli.py 启动时通过 DevSettings.for_expert("knowledge_expert", config_path=PROJ/"config.toml", env_path=PROJ/".env") 读取配置：

  • config.toml [llm.subagents.knowledge_expert]：决定 knowledge 专家用哪个 provider / model（noesis-knowledge 默认 provider="minimax"、model="MiniMax-M2.7"）。
  • **providers.toml**（与 config.toml 同级，自动发现）：给出每个 provider 的 base_url 和 api_key_env。

14. 关于 WSL 的必要性与场景方案

结论

开发 noesis-knowledge 并运行 python dev_cli.py，安装 WSL不是非装不可。 原生 Windows 即可，本指南全程 PowerShell 已验证可行。

为什么不装也行（针对”路径依赖、平台兼容”的担忧）

  1. 两项目源码都是纯 Python（无 .c/.cpp/.pyx/.so 需编译）；重依赖 faiss-cpu、pymupdf、h5py、numpy、scikit-learn 均提供 Windows 预编译 wheel，pip install 直接装二进制，不碰编译器。
  2. 无路径分隔符依赖：代码全程 pathlib.Path（如 dev_cli.py:29-31 的 PROJ = Path(__file__).parent、sys.path.insert(0, str(PROJ.parent / "noesis-contracts"))），config.toml 里 .dev/... 用正斜杠，Windows/Linux 都正常。无硬编码 /tmp、/home/...。
  3. readline 需手动打补丁（见第 8.1 步），打完后 Windows 走内置 input()，跨平台可用。
  4. config.toml 引用的外部非 Python 工具都不在 knowledge dev CLI 路径上：paddleocr-mcp（经 uvx，仅 /ingest OCR 用，uvx 本身跨平台）、rsync/cmake/mpicc（HPC/仿真专家用）、wolframscript/quarto/pandoc（论文专家用）。跑聊天 / 检索 / 公式提取一个都不需要。
  5. embedding 是远程 HTTP（10.181.9.191:18080），平台无关，只需网络可达。
  6. 本指南是 PowerShell 版，且 venv + contracts 已在 Windows 验证通过。

不装 WSL 的残留风险（提交到 Linux 时可能踩的坑）

风险 说明 缓解
导入大小写（最主要） Windows 文件系统大小写不敏感、Linux 敏感；大小写错的导入（如 from noesis_Knowledge ...）Win 能跑、Linux 崩 提交前在 Linux/容器跑一次冒烟；或 python -m compileall noesis_knowledge 全量编译检查
行尾 CRLF/LF git autocrlf 可能转换；Python 源码容忍，影响小 git config core.autocrlf false 或加 .gitattributes 统一 LF
可执行位 不影响（用 python dev_cli.py 而非 ./dev_cli.py） 无

什么场景才推荐装 WSL

  • 想让本地开发环境与生产 Linux 完全一致，提前暴露大小写等问题；
  • 日后要碰 HPC / rsync / 编译型仿真工具链（不在 knowledge 范围）；
  • 想统一用一套 Linux 工具链（docker / shell 脚本）。

推荐方案

  • 日常：原生 Windows 开发。
  • 提交前：在 Linux（CI / 容器 / 远端机器）做一次冒烟，至少跑：
  • 若反复出现”本地能跑、远端崩”且无法复现，再上 WSL 做开发；否则不必为纯 Python 的 knowledge 引入额外环境层。

附录 A：为什么 knowledge 安装必须 --no-deps 或裸名

noesis-knowledge/pyproject.toml 声明了：

第一行是 PEP 508 直接 URL 依赖。裸 pip install -e . 解析它时会：

  1. 判定第 4 步那个 file:///E:/.../noesis-contracts 的可编辑安装不满足 git+https://gitee.com/... 这条依赖（URL 协议/来源都不同）；
  2. 克隆 gitee 仓库到临时目录，构建非可编辑 wheel 装进 .venv\site-packages，覆盖本地可编辑安装–pip show noesis-contracts 里 Editable project location 那行会消失；
  3. 删除临时目录。

方法 A（--no-deps）：跳过依赖解析，既不碰 gitee，又保留 contracts 的本地可编辑状态。

方法 B（裸名 "noesis-contracts"）：把直接 URL 依赖改成普通名依赖，pip resolver 发现 contracts 已安装（无版本约束即满足），不再下载；同时保留 contracts 在依赖元数据里，pip check 更干净。

注：即便被覆盖，dev_cli.py:31 的 sys.path.insert(0, .../noesis-contracts) 仍会让运行时优先用本地源码–所以功能上不一定崩，但会多一次冗余拉取、丢失可编辑性、元数据自相矛盾。方法 A/B 是干净做法。

附录 B：两种安装方法对比

维度 方法 A：--no-deps + 手动清单 方法 B：裸名变体
命令数 2 条 1 条
改 tracked 文件 否 是（临时改 pyproject，装完还原）
装进 venv 的包/版本 latest（满足 >=） 完全相同
元数据含 contracts 依赖 含（git+https 形式，偶尔触发 pip check URL 告警） 含（裸名形式，pip check 干净）
维护成本 手动清单可能随上游漂移 自动跟踪 pyproject
还原风险 无 需装完立刻还原 +git diff 验证
适用 不想改任何源文件、或 pyproject 不可临时改 追求一条命令 + 干净元数据

选择建议：个人开发、能保证”装完立刻还原 + git diff 验证” -> 用方法 B；若不想动 tracked 文件、或要给团队固化流程 -> 用方法 A（并把手动清单沉淀成 requirements.txt）。两者结果等价。
