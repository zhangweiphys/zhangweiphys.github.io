WSL2 连接外网代理实战

摘要：在 Windows + WSL2 环境下使用 Codex CLI 等需要访问外网的工具时，常遇到 Clash 代理无法穿透 WSL 的问题。本文记录了从传统 NAT 模式排查防火墙双层拦截的完整历程，并最终迁移至 WSL2 镜像网络模式（Mirrored Networking）的实操方案。相比 NAT 模式，镜像模式以零防火墙配置、localhost 直连、端口不暴露局域网等优势，成为当前推荐的最佳实践。

1. 背景与目标

  • 环境：Windows 11 + WSL2 (Ubuntu 24.04) + Clash 系统代理（混合端口 7890）
  • 需求：WSL 内的 curl / git / npm / codex 等工具需通过 Windows 侧代理访问外网
  • 核心目标：
    1. 外网流量走 Clash 代理，国内流量直连
    2. 代理端口不暴露给局域网（防止蹭流量/节点风控）
    3. 配置稳定，不受 WSL 重启影响

2. 为什么推荐镜像模式（Mirrored）

在尝试修复 NAT 模式后，我们发现其维护成本远高于直接切换镜像模式。以下是两种模式的对比：

维度 NAT 模式（传统） 镜像模式（推荐）
代理地址 动态网关 IP（重启后变化） 127.0.0.1（固定）
防火墙 需处理程序级 Block + Hyper-V 防火墙 无需任何防火墙配置
局域网暴露 需额外规则限制，否则端口开放 仅 localhost 回环，天然隔离
Clash 设置 必须开启「允许局域网」 可关闭「允许局域网」
代理变量 需 .bashrc 动态获取网关 autoProxy 自动同步或固定 127.0.0.1

结论：镜像模式实现了“共享 localhost + 端口不暴露 + 零防火墙手术”的一箭三雕，是当前 WSL2 网络配置的优选方案。

4. 注意事项与常见坑

  1. 端口共享：镜像模式下 WSL 与 Windows 共享 localhost，WSL 内启动的 Web 服务会占用 Windows 同端口，注意避免冲突。
  2. Docker Desktop 兼容性：Docker Desktop 与镜像模式历史上存在兼容性问题，如需使用请提前查阅官方最新文档。
  3. Interop 问题：切换网络模式后若遇到 WSL interop 异常（如 “Invalid argument”），可尝试 wsl --shutdown 后重试；若仍无效则运行 wsl --update。

5. （附录）NAT 模式排错备忘（可选）

以下为 NAT 模式下的排查经验记录，仅供遇到类似问题时参考。如果你已采用镜像模式，可跳过本节。

三个易踩坑点

  1. /etc/resolv.conf 中的 nameserver 是 DNS 隧道虚拟地址，不能作为代理主机 IP
  2. NAT 模式下宿主机 IP = WSL 默认网关，且每次重启后变化，必须动态获取

防火墙双层拦截真凶

当 WSL 无法连接 Windows 代理端口时，常见原因有两层：

  1. 程序级 Block 规则：首次开启「允许局域网」时误点”拒绝”，系统自动生成 clash-win64 入站 Block 规则。程序级 Block 优先级高于端口级 Allow，导致按端口查不到问题。
  2. Hyper-V 防火墙：WSL 专属网络层默认拦截入站，普通 Get-NetFirewallRule 查不到，需用 Set-NetFirewallHyperVVMSetting 操作。

诊断技巧

  • 区分拒绝与丢弃：timeout 3 bash -c 'echo > /dev/tcp/<ip>/<port>' —— 立即报 Connection refused = 主动拒绝（有 RST）；超时退出码 124 = 静默丢弃（被过滤）
  • 对照实验：用已知开放端口（如 445/SMB）做对照，确认网络路径本身是否正常
  • 隔离实验：手机连同一 WiFi 测试电脑 IP:7890，能通则拦截仅在 WSL 路径

6. Codex 省额度策略：主 Agent 规划 + 子 Agent 执行

Codex 的使用受滚动窗口和周配额双重限制。为了最大化利用额度，推荐采用 “主 Agent 负责高阶规划与决策，子 Agent 负责批量执行” 的分层策略。以下是一份 ~/.codex/config.toml 配置参考：

策略说明

层级 角色 模型选择 Reasoning Effort 适用场景
主 Agent 规划者/决策者 高能力模型 日常 low / Plan high 任务拆解、架构设计、复杂调试、代码审查
子 Agent 执行者 轻量模型 high Slurm 提交/监控、批量统计、文件处理、例行脚本

使用建议

  • 分工原则：让主 Agent 做”难活”（手稿阅读、复杂逻辑推理），子 Agent 做”批量活”（重复性操作、格式化任务）。两者不要同时修改同一批文件。
  • 临时全自动：对于纯机械任务，可用 codex -a never 跳过所有确认。
  • 安全兜底：删除作业、取消任务等高危操作应通过 ~/.codex/rules/default.rules 强制询问或硬禁，不完全依赖 approval_policy。
  • 额度监控：ChatGPT Plus 为 5 小时滚动窗口 + 周配额双重限制，耗尽后可等待重置或购买额外用量。合理规划主/子 Agent 调用比例可有效延长使用时间。
